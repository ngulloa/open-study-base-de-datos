Redundancia, dependencias funcionales y llaves

Motivación del diseño relacional, anomalías, dependencias funcionales, superllaves y llaves.

Intuición: por qué diseñar relaciones

Una base de datos puede almacenar información correcta y aun así tener un mal esquema. Esto plantea una pregunta de diseño: ¿conviene almacenar todo en una sola relación o fragmentarlo en muchas relaciones pequeñas? Ninguno de los extremos es correcto por sí mismo.

El objetivo es diseñar un esquema que favorezca:

  • integridad y consistencia de los datos;
  • representación precisa del dominio;
  • eficiencia en tiempo y espacio;
  • flexibilidad frente a cambios.

Redundancia y anomalías

Consideremos una relación deliberadamente redundante:

rut estudiante carrera codigo curso creditos semestre
r2 Ben Computación PROG201 Programación Avanzada 10 2025-1
r2 Ben Computación BD101 Bases de Datos 10 2025-2
r3 Zoe Computación PROG201 Programación Avanzada 10 2024-2
r3 Zoe Computación BD101 Bases de Datos 10 2025-2

La carrera de Ben se repite; también el nombre y créditos de cada curso.

La redundancia puede producir tres anomalías clásicas. (Silberschatz et al. 2020)

Anomalía de actualización

Si BD101 cambia su nombre, hay que modificar varias filas. Si una queda sin actualizar, la relación pasa a afirmar dos nombres distintos para el mismo código.

Anomalía de eliminación

Si eliminamos la última inscripción de cierto curso y sus datos solo existen dentro de esta relación, podemos perder accidentalmente el nombre y sus créditos.

Anomalía de inserción

Si queremos registrar un curso nuevo antes de que tenga estudiantes inscritos, el esquema combinado puede obligarnos a inventar datos de inscripción o usar nulos innecesarios.

Estas anomalías también pueden aparecer en otros dominios, como un catálogo de películas que repite datos de cada estudio productor. Su causa común es almacenar repetidamente información determinada por dependencias entre atributos.

Dependencias funcionales

Sea \(R\) una relación nombrada y sean \(\bar A\) y \(\bar B\) listas de atributos distintos de \(R\). En el razonamiento con dependencias importa su conjunto de atributos, no el orden. Escribiremos \(\{\bar A\}\) para ese conjunto; el complemento se toma dentro de \(att(R)\).

NotaDefinición formal

Una dependencia funcional tiene la forma

\[ \bar A\to\bar B. \]

La relación \(R\) satisface esa dependencia, escrito

\[ R\models\bar A\to\bar B, \]

si para todas \(\bar\tau_1,\bar\tau_2\in R\):

\[ \pi_{\bar A}(\bar\tau_1)=\pi_{\bar A}(\bar\tau_2) \quad\Longrightarrow\quad \pi_{\bar B}(\bar\tau_1)=\pi_{\bar B}(\bar\tau_2). \]

(Arenas et al. 2022)

Intuitivamente: si dos tuplas coinciden en \(\bar A\), entonces deben coincidir en \(\bar B\).

Dependencias del dominio universitario

En el esquema acordado, son naturales restricciones como:

\[ rut\to nombre\ carrera \]

para Estudiante,

\[ codigo\to nombre\ creditos \]

para Curso, y

\[ pid\to nombre\ departamento \]

para Profesor.

Estas dependencias no se justifican porque «casualmente» la instancia actual tenga valores distintos. Representan reglas del dominio: un RUT identifica los datos de un estudiante; un código identifica la información de un curso; un PID identifica un profesor.

AdvertenciaInstancia versus restricción del dominio

Una dependencia funcional no debe inferirse solo observando una instancia. Una tabla pequeña puede satisfacer accidentalmente muchas dependencias que dejarían de cumplirse al insertar nuevos datos. Las dependencias relevantes para diseño son restricciones que el dominio pretende mantener.

Dependencias triviales

Una dependencia

\[ \bar A\to\bar B \]

es trivial cuando los atributos de \(\bar B\) ya están contenidos en \(\bar A\). En ese caso siempre se satisface, porque dos tuplas que coinciden en \(\bar A\) necesariamente coinciden en cualquier subconjunto de esos atributos.

Superllaves

NotaSuperllave de una instancia

Sea \(\bar A^c\) el complemento de los atributos \(\bar A\) dentro de \(R\). \(\bar A\) es una superllave de \(R\) si y solo si

\[ R\models\bar A\to\bar A^c. \]

Es decir, \(\bar A\) determina todos los demás atributos.

Equivalentemente:

\[ \bar A\text{ es superllave} \iff \forall\bar\tau_1,\bar\tau_2\in R, \; \pi_{\bar A}(\bar\tau_1)=\pi_{\bar A}(\bar\tau_2) \Rightarrow \bar\tau_1=\bar\tau_2. \]

Por tanto, una superllave identifica unívocamente cada tupla de la instancia. En diseño, \(\bar A\) es una superllave bajo \(F\) si lo hace en toda relación que satisface las dependencias \(F\), es decir, si \(F\models\bar A\to att(R)\). La clausura permite comprobar esta propiedad del esquema.

Llaves

Una llave es una superllave minimal:

  1. \(\bar A\) es superllave;
  2. ningún subconjunto propio de sus atributos sigue siendo superllave.

Para Estudiante(rut,nombre,carrera), supongamos que rut identifica unívocamente a cada estudiante y que ni nombre ni carrera, solos o combinados, garantizan esa identificación. Entonces:

  • rut es llave;
  • rut nombre es superllave, pero no llave, porque contiene una superllave más pequeña.

Para Inscribe(rut,codigo,semestre), si el dominio garantiza a lo sumo una inscripción por estudiante, curso y semestre, el conjunto de los tres atributos identifica una inscripción. Para que sea una llave candidata, además ningún subconjunto propio debe garantizar esa identificación. Esta es una decisión de modelamiento que debe confirmarse con los requisitos del dominio.

NotaTerminología

El término inglés para superllave es superkey. Una llave minimal también se llama llave candidata (candidate key). (Silberschatz et al. 2020; Ramakrishnan y Gehrke 2003)

Llaves en SQL

En SQL, una llave primaria se declara así:

CREATE TABLE Estudiante (
  rut     VARCHAR(12),
  nombre  VARCHAR(100),
  carrera VARCHAR(100),
  PRIMARY KEY (rut)
);

Para una llave compuesta:

CREATE TABLE Inscribe (
  rut      VARCHAR(12),
  codigo   VARCHAR(20),
  semestre VARCHAR(10),
  PRIMARY KEY (rut, codigo, semestre)
);

PRIMARY KEY declara una llave primaria elegida para la tabla. La teoría puede admitir más de una llave candidata; SQL distingue cuál se declara como primaria. (Silberschatz et al. 2020)

Qué problema resolvimos y cuál falta

Las dependencias funcionales formalizan regularidades que explican redundancia y permiten reconocer llaves. Aún falta responder preguntas como:

  • ¿qué dependencias se deducen de otras?
  • ¿cómo decidir algorítmicamente si un conjunto de atributos es superllave?
  • ¿cómo descomponer una relación sin introducir información falsa?

Estas preguntas conducen a implicación y clausura y luego a descomposiciones.

Resumen

  • La redundancia puede producir anomalías de actualización, eliminación e inserción.
  • Una dependencia funcional \(\bar A\to\bar B\) exige que coincidencia en \(\bar A\) implique coincidencia en \(\bar B\).
  • Las dependencias relevantes son restricciones del dominio, no coincidencias accidentales de una instancia.
  • Una superllave determina todos los atributos; una llave es una superllave minimal.
  • PRIMARY KEY materializa en SQL una llave elegida para la tabla.
