Subconsultas

Consultas anidadas en FROM y WHERE, correlación, EXISTS, IN, consultas escalares y ANY/ALL.

Intuición y concepto

Una subconsulta es una consulta SQL usada dentro de otra consulta. Permite componer consultas, del mismo modo que el álgebra relacional compone expresiones y la lógica combina subfórmulas. (Silberschatz et al. 2020)

Las formas principales son:

  1. anidación en FROM;
  2. anidación en WHERE mediante IN;
  3. EXISTS y NOT EXISTS;
  4. subconsultas que producen un valor;
  5. comparaciones con ANY y ALL.

Subconsultas en FROM

Una consulta puede producir una relación intermedia y darle un alias:

SELECT E.nombre, I.codigo
FROM Estudiante AS E,
     (
       SELECT rut, codigo
       FROM Inscribe
       WHERE semestre = '2025-2'
     ) AS I
WHERE E.rut = I.rut;

Conceptualmente, la subconsulta define primero una relación temporal I; la consulta exterior la combina con Estudiante.

En álgebra relacional, esto no requiere un operador nuevo: es simplemente una subexpresión.

IN

IN pregunta si un valor aparece en el resultado de una subconsulta de una columna:

SELECT nombre
FROM Estudiante
WHERE rut IN (
  SELECT rut
  FROM Inscribe
  WHERE codigo = 'BD101'
);

En lógica, el valor externo se conecta con un testigo producido por la subconsulta. En álgebra, suele expresarse mediante join o semijoin.

NOT IN

SELECT nombre
FROM Estudiante
WHERE rut NOT IN (
  SELECT rut
  FROM Inscribe
  WHERE codigo = 'BD101'
);

parece expresar «estudiantes no inscritos en BD101», pero hay una advertencia importante: si la subconsulta puede producir NULL, la lógica de tres valores puede hacer que NOT IN descarte filas inesperadamente. El resultado puede incluso ser vacío: una comparación que queda en UNKNOWN no pasa el filtro WHERE.

AdvertenciaNOT IN y NULL

Cuando la subconsulta puede contener NULL, NOT EXISTS suele reflejar con mayor claridad la intención «no existe una coincidencia». Revisa NULL y lógica de tres valores antes de transformar mecánicamente NOT IN.

EXISTS

EXISTS es verdadero si la subconsulta produce al menos una fila.

SELECT C.nombre
FROM Curso AS C
WHERE EXISTS (
  SELECT 1
  FROM Dicta AS D
  WHERE D.codigo = C.codigo
);

La subconsulta está correlacionada: usa C.codigo, un valor de la consulta exterior.

La referencia externa vincula la evaluación de la subconsulta con la fila de la consulta exterior.

NOT EXISTS

NOT EXISTS expresa ausencia de testigos:

SELECT C.nombre
FROM Curso AS C
WHERE NOT EXISTS (
  SELECT 1
  FROM Requisito AS R
  WHERE R.codigo = C.codigo
);

En lógica:

\[ Q(n)\leftarrow \exists c\exists cr.\; Curso(c,n,cr)\land \neg\exists p.\;Requisito(c,p). \]

Esta correspondencia hace de NOT EXISTS una herramienta natural para consultas «ninguno» o «nunca».

Subconsultas escalares

Una subconsulta puede usarse donde se espera un solo valor:

SELECT nombre
FROM Curso
WHERE creditos > (
  SELECT AVG(creditos)
  FROM Curso
);

Una subconsulta escalar debe producir una columna y, como máximo, una fila. Si no produce filas, su valor es NULL; si produce varias, los motores que exigen cardinalidad escalar reportan un error.

El comportamiento exacto ante casos no escalares puede depender del RDBMS, por lo que no debe construirse una consulta suponiendo una selección arbitraria de una fila.

ANY y ALL

Una comparación puede cuantificarse sobre el resultado de una subconsulta:

expresion > ANY (subconsulta)

y

expresion > ALL (subconsulta)

Intuitivamente:

  • > ANY exige que la comparación sea verdadera para al menos un valor;
  • > ALL exige que sea verdadera para todos los valores relevantes de la subconsulta.
AdvertenciaDialectos

SQLite no implementa comparaciones cuantificadas de la forma > ANY (subconsulta) o > ALL (subconsulta). En ese motor se necesitan otras formulaciones; al traducir, hay que preservar también el comportamiento ante NULL y resultados vacíos. Consulta la sintaxis de expresiones de SQLite y las comparaciones cuantificadas de PostgreSQL.

Correlación y desanidamiento

Una consulta correlacionada se evalúa conceptualmente en relación con cada fila de la consulta exterior. Esto no significa que el motor deba implementarla literalmente así: el optimizador puede reescribirla.

Al sustituir un EXISTS correlacionado por un join, los duplicados pueden cambiar.

Ejemplo:

SELECT E.nombre
FROM Estudiante AS E
WHERE EXISTS (
  SELECT 1
  FROM Inscribe AS I
  WHERE I.rut = E.rut
);

no es observablemente equivalente, bajo semántica de duplicados, a:

SELECT E.nombre
FROM Estudiante AS E
JOIN Inscribe AS I
  ON I.rut = E.rut;

si un estudiante tiene varias inscripciones. La segunda consulta puede repetir su nombre. Aplicar DISTINCT solo a E.nombre tampoco preserva siempre el resultado: eliminaría las repeticiones debidas a estudiantes diferentes con el mismo nombre. Una transformación equivalente une cada estudiante con una sola aparición de su RUT:

SELECT E.nombre
FROM Estudiante AS E
JOIN (SELECT DISTINCT rut FROM Inscribe) AS I
  ON I.rut = E.rut;

Elegir una forma

No existe una única sintaxis «correcta» para toda consulta. Una regla útil es expresar directamente la intención:

  • pertenencia a un conjunto de valores → IN;
  • existencia de una fila relacionada → EXISTS;
  • ausencia de una fila relacionada → NOT EXISTS;
  • comparación contra un único resultado → subconsulta escalar;
  • relación intermedia reutilizable en FROM → subconsulta derivada.

La equivalencia con álgebra y lógica permite justificar estas elecciones en vez de memorizarlas. (Ramakrishnan y Gehrke 2003; Silberschatz et al. 2020)

Resumen

  • Una subconsulta es una consulta usada como componente de otra.
  • Las subconsultas en FROM actúan como relaciones intermedias.
  • IN, EXISTS y NOT EXISTS expresan pertenencia, existencia y ausencia.
  • Una subconsulta correlacionada depende de valores de la consulta exterior.
  • Al desanidar hay que controlar duplicados.
  • NOT IN requiere especial cuidado cuando interviene NULL.
